Claude Science + MCP

CiteProof MCP tool reference

This page documents all 40 tools in CiteProof MCP 0.3.0. Each entry lists the arguments, the limits the server enforces, and a realistic request and result. The tool names, fields and caps mirror the shipped schemas.

The division of labour

Claude Science searches, reads and writes. CiteProof MCP stores the protocol, PRISMA counts, screening decisions, extracted evidence, claims and risk-of-bias judgements, validates their shape, checks supplied quotes and computes the counts. The server contains no language model and does not search for papers.

How Claude Science and CiteProof MCP fit together

A research agent can draft a systematic review, but the decisions behind the draft need a record: why a paper was excluded, which studies were included, what each study reported, and whether the cited sentence appears in the source. CiteProof MCP is that record.

Claude Science: research agent

Runs searches, retrieves papers, reads full text, makes inclusion and exclusion judgements, extracts results, grades risk of bias and drafts the report. Every scientific judgement comes from the agent or its human reviewer.

CiteProof MCP: audit layer

Stores those judgements in a local review file, rejects malformed input, checks that quotes appear in the supplied text, computes deduplication and PRISMA counts, and exports the audit trail.

The MCP server is a separate component of the CiteProof repository. It does not use the research app, its model endpoint or its search keys, and it needs no model API key.

Architecture and data flow

1. Research agent Claude Science searches, reads and decides. It supplies each decision and, where required, the source text and quote.
2. CiteProof MCP A local stdio server validates arguments, checks quotes, computes counts and writes one SQLite review file.
3. Audit output review_status reports gaps and next steps. export_bundle returns one Markdown or JSON document.

Each review is one SQLite file at <CITEPROOF_MCP_HOME>/reviews/<review_id>.db. Writes use one immediate transaction with a 30 second busy timeout, so concurrent calls wait instead of failing with a locked database. Read tools never change the record.

Every tool returns JSON with an ok boolean. A successful result adds tool-specific fields. A handled failure returns {"ok": false, "error": "..."}.

What the server does not do

  • It does not search literature, query a database or open a paper. The agent supplies every record.
  • It does not contain an LLM and does not make inclusion, extraction, claim or risk-of-bias judgements.
  • It does not prove that a study is valid, that a claim is scientifically true or that a review is complete.
  • It does not turn a resolved DOI into evidence. A registered DOI only proves that the identifier exists; citation matching is called resolved, never verified.
  • It does not upload review data. Exports are returned as text; only export_bundle with save=true also writes the document under <CITEPROOF_MCP_HOME>/exports/.
  • claude.ai web custom connectors cannot start a local stdio process, so they are not supported.

Connect CiteProof MCP to Claude Science

The recommended install is a Local command connector that runs npx -y citeproof-mcp. It was checked on Claude Science 0.1.70 on Windows 11 (native sandbox): the connector starts and lists all 24 tools in version 0.2.1; version 0.3.0 exposes 40 tools (not yet tested in Claude Science). The connector runs inside a sandbox that can read only its own workspace folder and Claude Science's bundled runtime, and that cannot reach astral.sh. For that reason the launcher does not need to download uv there: it runs the server code it carries with the sandbox's own python3, which already provides mcp, pydantic and httpx.

Prerequisites

  • Claude Science with Connectors available under Customize.
  • npx. The command is npx -y citeproof-mcp, which needs Node.js 18 or newer.
  • No model API key. The server makes no model calls.
  • This repository, only if you use the bundle fallback below. The build script uses only the Python standard library.

Install the Claude Science connector

  1. Add a connector. Open Customize, then Connectors, then Add connector, then Local command.
  2. Name it and enter the command. The name allows lowercase letters, digits and hyphens only, so use citeproof. The command line is npx -y citeproof-mcp.
  3. Optional: set the data folder. Under Advanced settings, add the environment variable CITEPROOF_MCP_HOME to keep review files in a folder you choose. Without it, review files go to ~/.citeproof-mcp inside the sandbox.
  4. Wait for the first start. The first start downloads the package and can take about half a minute.
  5. Confirm 40 tools. The connector page should list every tool from review_create to review_history (40 tools in 0.3.0; 24 in 0.2.1). Claude Science asks for approval before each tool run by default; set a tool to always allow only after you trust it.
npx -y citeproof-mcp

After a new release, Claude Science keeps the previous npx copy in the connector workspace (.../workspaces/_mcp-citeproof/.npm/_npx). If the old version keeps loading, delete that folder and turn the connector off and on. Review data survives this.

Fallback: build a bundle

If the npx command cannot start in your Claude Science, copy the server into the connector workspace and start it with Claude Science's own python3. This path was checked on Claude Science 0.1.67 on Windows 11.

  1. Create the connector workspace. Add a Local command connector named citeproof with the command python3 placeholder.py. It will fail; the first start creates the workspace folder. If the folder does not appear, create it by hand in the next step.
  2. Find the workspace folder. On Windows it is C:/Users/<you>/.claude-science/orgs/<org-id>/workspaces/_mcp-citeproof. The command claude-science logs also prints it as cwd in the sandbox policy lines.
  3. Build the bundle into that folder. Run the command below from the repository root. The script refuses a folder that holds other files, so passing the workspace folder by mistake cannot delete your data folder.
  4. Point the connector at the bundle. Remove the placeholder and add the connector again. Use forward slashes in the command; backslashes are stripped by the form.
  5. Set the data folder. Add the environment variable CITEPROOF_MCP_HOME so review files stay inside the sandbox workspace.
python MCP/scripts/build_claude_science_bundle.py "C:/Users/<you>/.claude-science/orgs/<org-id>/workspaces/_mcp-citeproof/bundle"
python3 C:/Users/<you>/.claude-science/orgs/<org-id>/workspaces/_mcp-citeproof/bundle/run.py
CITEPROOF_MCP_HOME=C:/Users/<you>/.claude-science/orgs/<org-id>/workspaces/_mcp-citeproof/data

After a new release, run the build script again into the same bundle folder, then remove and re-add the connector with the same settings. The running process keeps old code in memory, and the Connectors page has no restart button when the connector is healthy. Review data in the data folder survives this.

Confirm the tools are available

Ask the client to list its tools, or open the connector details. A healthy install shows 40 tools with the names on this page. If fewer appear, an older server process is still running: remove the connector and add it again.

The first useful call is review_create. If it succeeds, the server is running and can write to CITEPROOF_MCP_HOME.

Installing is not using

A successful install only makes the tools callable. It does not create a review, run a search or add records. Ask Claude Science to follow the workflow on this page, or give it the instruction “use CiteProof MCP for the review record and call review_status before moving to the next stage”.

Use one data folder per client

If two clients should share reviews, give them the same CITEPROOF_MCP_HOME. Do not point two servers at the same review file and expect independent writers; writes serialise on the SQLite file.

Follow the end-to-end review workflow

The order matters because later tools read earlier records. Run review_status at any point to learn the current phase and what is missing.

Stage What to do Tools
1. Create or recover Create the review file, or list existing reviews and reuse a review_id. review_create, review_list
2. Protocol Record the question, populations, outcomes, eligibility and search plan before screening. protocol_record
3. Searches Record one row per database, query and run date, with the hit count. prisma_record_search
4. Deduplication and validation Deduplicate the complete exported set and record the count (a partial batch is analysed but not recorded), then check known seed papers against the retrieved records. dedup_papers, prisma_record_dedup, recall_seed_record, recall_check
5. Screening and agreement Record reviewer types, set blind stages before anyone screens, screen titles and abstracts then full text under each reviewer's own name, close the stage, compute agreement, then record consensus under primary. reviewer_record, screening_stage_set, screening_record, screening_record_many, screening_list, screening_stage_close, screening_agreement, prisma_status
6. Paper and study identity Resolve aliases and group reports into studies to prevent double-counting participants. paper_resolve, paper_alias_record, study_link, study_unlink, study_overview
7. Evidence and statistics Record outcome rows with verified quotes and check statistical consistency of ratios, intervals and 2×2 data. evidence_record, evidence_table, stats_check_ratio_ci, stats_recompute_2x2, stats_check_evidence
8. Risk of bias Record each domain for the chosen tool, then compute the overall judgement by the published rule. rob_record, rob_summary
9. Claims Record each key claim with a label, reason and quote, then find weak claims in the draft. claim_record, claim_report
10. Citations and prose Check DOIs against Crossref and doi.org, and resolve author-year citations against the paper list. verify_dois, resolve_citations, lint_prose
11. Excluded studies and manuscript Reconcile full-text exclusion reasons and audit draft manuscript sections against recorded review data. prisma_flow_diagram, prisma_checklist, prisma_excluded_studies, manuscript_check
12. History and export Inspect the event history and export the audit bundle, optionally saved to disk with its SHA-256. review_history, export_bundle, review_status

When you resume a review in a new session, call review_status first. It reports the phase, missing protocol fields, PRISMA completeness, reviewer names, included studies, extraction and risk-of-bias coverage, claim counts, DOI checks and source-text changes.

Tool reference

Arguments marked optional may be omitted. Every result also has ok. List results are capped at 200 items unless the entry says otherwise, and a cut list sets truncated: true. Paper references use the forms described in Paper identity; use the same form for a paper in every tool.

Review setup and core checks

review_create

Creates a review file and returns its identifier. Every other tool needs that review_id.

ArgumentTypeRequiredNotes
titlestringYesMaximum 500 characters.
questionstringYesMaximum 2,000 characters.
year_minintegerNo1800 to 3000. Must not exceed year_max.
year_maxintegerNo1800 to 3000. Must not be below year_min.

Limits. The id is generated by the server and matches ^[a-z0-9_-]{6,40}$. Creating a review never reuses an existing file.

Example request.

{"title": "Teleradiology turnaround times: a systematic review", "question": "In adults, what is the effect of teleradiology on radiology report turnaround time?", "year_min": 2010, "year_max": 2026}

Example result.

{"ok": true, "review_id": "rev-9f3c2a1b", "next_step": "Record the protocol with protocol_record (PICO, eligibility criteria, databases, search strategy)."}

review_list

Lists review files in the current CITEPROOF_MCP_HOME, newest first. Use it to recover an id when you resume work.

ArgumentTypeRequiredNotes
limitintegerNoDefault 50. Capped at 200.

Example request.

{"limit": 10}

Example result.

{"ok": true, "reviews": [{"review_id": "rev-9f3c2a1b", "title": "Teleradiology turnaround times: a systematic review", "question": "In adults, what is the effect of teleradiology on radiology report turnaround time?", "created_at": "2026-10-25T09:14:00Z", "year_min": 2010, "year_max": 2026}], "count": 1}

verify_dois

Checks DOIs against Crossref and doi.org. This is the only tool that uses the network. With a review_id, the results are saved for review_status and export_bundle.

ArgumentTypeRequiredNotes
doisarray of strings, or one stringYesUp to 100 DOIs. One string may separate DOIs with spaces, commas or new lines. doi: and doi.org prefixes are normalised; duplicates are removed case-insensitively.
review_idstringNoSaves the result. The review must exist.

Status. resolved means the registry returned a record. not_found means doi.org returned 404. unverified means the registry could not be reached, so there is no verdict. invalid means the value was not DOI-shaped and was never sent. retracted is true or false only for Crossref records.

Limits. Fixed HTTPS hosts, no redirect following, 15 second timeout. A redirect from doi.org is read as registered. No other host is contacted.

Example request.

{"dois": ["10.1136/bmj.n71", "https://doi.org/10.1371/journal.pmed.1003583"], "review_id": "rev-9f3c2a1b"}

Example result.

{"ok": true, "results": [{"doi": "10.1136/bmj.n71", "input": "10.1136/bmj.n71", "status": "resolved", "title": "The PRISMA 2020 statement: an updated guideline for reporting systematic reviews", "year": 2021, "journal": "BMJ", "authors": "Page MJ, McKenzie JE, Bossuyt PM", "retracted": false, "registry": "crossref"}, {"doi": "10.1371/journal.pmed.1003583", "input": "https://doi.org/10.1371/journal.pmed.1003583", "status": "resolved", "title": "PRISMA 2020 explanation and elaboration", "year": 2021, "journal": "PLOS Medicine", "authors": "Page MJ, Moher D, Bossuyt PM", "retracted": false, "registry": "crossref"}], "summary": {"checked": 2, "resolved": 2, "not_found": 0, "unverified": 0, "invalid": 0, "retracted": 0}, "offline": false, "saved": true, "note": "Registry lookups only: a resolved DOI is real, which says nothing about whether it supports a claim."}

resolve_citations

Matches inline citations in a draft against a supplied paper list. It rewrites common author-year forms such as Smith et al. (2020), (Smith 2020) and (Smith, 2020a) before matching. Groups that contain a DOI or URL are left alone.

ArgumentTypeRequiredNotes
textstringYesThe draft or section to check.
papersarray of objectsYesUp to 2,000 papers. Each object has title, authors (list or A; B) and year; doi is optional.

Result notes. resolved excludes ambiguous matches. Numeric citations such as [1] are counted, not resolved. orphan_papers lists papers in the supplied list that the text never cites.

Limits. A match is resolution, not verification: it shows that a citation points at a paper in the list, not that the paper supports the sentence.

Example request.

{"text": "Teleradiology reduced turnaround time (Smith et al., 2021). A later trial disagreed (Jones and Lee, 2023).", "papers": [{"title": "Teleradiology turnaround in rural hospitals", "authors": ["Smith J", "Patel R"], "year": 2021, "doi": "10.1000/example.2021"}, {"title": "Turnaround after overnight teleradiology", "authors": ["Jones A", "Lee K"], "year": 2023}]}

Example result.

{"ok": true, "citations_found": 2, "resolved": 2, "ambiguous": [], "unresolved": [], "orphan_papers": [], "doi_citations_checked": 0, "numeric_citations_found": 0, "truncated": false, "note": "Resolved means the citation points at a supplied paper, not that the paper supports the sentence."}

lint_prose

Runs deterministic prose checks on a draft. Findings are advisory: they flag style and trace-leakage patterns, not factual errors.

ArgumentTypeRequiredNotes
textstringYesMarkdown draft or section.

Codes. EMDASH (too many em-dashes per 1,000 words), HONEST (framing such as “to be honest”), PROCNOTE (process narration), PARENDOI (an unencoded parenthesis in a DOI link), LONGHEAD (sentence-like headings) and FLATSTRUCT (many top-level sections with no subsections).

Limits. The result is advisory and nothing is saved. Text is treated as data; retrieved text cannot inject a new instruction.

Example request.

{"text": "## Why teleradiology matters for the whole health system and every patient\n\nTo be honest, the evidence is mixed."}

Example result.

{"ok": true, "issues": [{"code": "HONEST", "note": "'To be honest': drop the framing, write the sentence it was guarding"}, {"code": "LONGHEAD", "note": "1 headings read as sentences; shorten to <=6-word noun phrases"}], "issue_count": 2, "advisory": true}

Protocol

protocol_record

Records or updates the review protocol. Omitted fields keep their current value, so calling with only review_id reads the protocol. An empty string or empty list clears a field.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
population, intervention, comparator, outcomes, study_designs, inclusion_criteria, exclusion_criteria, databases, search_strategy, languages, registration, synthesis_methodstring or list of stringsNoList fields accept a list or one string split on new lines and semicolons.
rob_toolstringNoOne of rob2, robins_i, nos, nos_case_control, mixed, none.
year_min, year_maxintegerNoRecorded as the protocol year range.

Required fields. population, intervention, outcomes, inclusion_criteria, exclusion_criteria, databases and search_strategy. Recommended: comparator, study_designs, the year range, languages, registration, rob_tool and synthesis_method.

Amendments. Every change is logged. Changing a field that already had a value is reported as an amendment.

Example request.

{"review_id": "rev-9f3c2a1b", "population": "Adults referred for diagnostic imaging", "intervention": "Teleradiology reporting", "comparator": "On-site radiology reporting", "outcomes": ["Report turnaround time", "Diagnostic agreement"], "inclusion_criteria": ["Primary comparative study", "Report turnaround time measured"], "exclusion_criteria": ["Conference abstract only", "No quantitative result"], "databases": ["PubMed", "Embase"], "search_strategy": "(\"teleradiology\" OR \"telemedicine\") AND \"turnaround time\"", "rob_tool": "robins_i"}

Example result.

{"ok": true, "protocol": {"population": "Adults referred for diagnostic imaging", "intervention": "Teleradiology reporting", "rob_tool": "robins_i"}, "updated_fields": ["population", "intervention", "comparator", "outcomes", "inclusion_criteria", "exclusion_criteria", "databases", "search_strategy", "rob_tool"], "complete": true, "missing_required": [], "missing_recommended": ["study_designs", "year_range", "languages", "registration", "synthesis_method"], "amendments": 0, "next_step": "Protocol complete. Run the searches and log each one with prisma_record_search."}

PRISMA and screening

prisma_record_search

Records one database search. The same source, query and run date replaces the hit count instead of adding a row, so a retried call cannot double-count.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
sourcestringYesDatabase name, matched case-insensitively.
querystringYesThe query as run.
date_runstringYesA real YYYY-MM-DD date. A future date is a warning.
hitsintegerYesRecords returned by this search.

Important. Adding a search or changing a hit count clears the review's deduplication record, because the old count belonged to a different set of records. The result says so in warnings. Re-sending the same search with the same hits changes nothing.

Example request.

{"review_id": "rev-9f3c2a1b", "source": "PubMed", "query": "teleradiology AND turnaround time", "date_run": "2026-10-20", "hits": 412}

Example result.

{"ok": true, "search_id": 1, "updated": false, "records_identified": 412, "records_by_source": {"PubMed": 412}, "searches_recorded": 1, "warnings": []}

dedup_papers

Detects duplicate records in an exported set. Same paper means the same normalised DOI, the same PMID, or the same normalised title of at least 20 characters with the same year and first-author surname. Matching is transitive.

ArgumentTypeRequiredNotes
papersarray of objectsYesUp to 10,000 exported records. Fields: id, doi, pmid, title, year, authors or first_author, abstract.
review_idstringNoRecords the count only when the call covers every exported record.

Recording rule. A review has one deduplication count. It is saved only when review_id is given and the call covers every exported record, that is, records_checked equals the total hits from prisma_record_search. A partial or batched call is analysed but not saved: the result has recorded: false and a warning, and the review keeps its previous deduplication record. When a call is saved, it replaces any earlier record. For a set larger than 10,000 records, or one you deduplicated elsewhere, record the whole-review count with prisma_record_dedup.

What is kept. The record with the most complete metadata is kept. Records are not merged, so copy any field you need from a removed record before discarding it. A same-title record with a different year or author is listed in possible_duplicates instead of merged. Dedup records canonical aliases and conflict proposals (aliases_recorded, alias_conflicts).

Example request.

{"review_id": "rev-9f3c2a1b", "papers": [{"id": "p1", "doi": "10.1000/example.2021", "title": "Teleradiology turnaround in rural hospitals", "year": 2021, "first_author": "Smith"}, {"id": "p2", "pmid": "12345678", "title": "Teleradiology turnaround in rural hospitals", "year": 2021, "first_author": "Smith"}, {"id": "p3", "doi": "10.1000/example.2023", "title": "Turnaround after overnight teleradiology", "year": 2023, "first_author": "Jones"}]}

Example result. This example sends 3 of 412 recorded hits, so nothing is recorded.

{"ok": true, "records_checked": 3, "unique_records": 2, "duplicates_removed": 1, "removed_indices": [1], "clusters": [{"kept_index": 0, "kept_id": "p1", "member_indices": [0, 1], "matched_on": ["title_year_author"], "conflicting_dois": false}], "possible_duplicates": [], "truncated": false, "recorded": false, "method": "dedup_papers: exact DOI, then PMID, then normalised title + year + first-author surname", "warnings": ["3 records were checked but the recorded searches total 412 hits, so the duplicate count was NOT recorded (the review keeps its previous dedup record). Send every exported record in one call. If the review has more than 10000 records, or you deduplicated elsewhere, record the whole-review count with prisma_record_dedup."]}

prisma_record_dedup

Records a whole-review duplicate count when deduplication was done elsewhere, for example in a reference manager. It replaces any existing dedup record.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
duplicates_removedintegerYesCannot exceed the recorded hits.
methodstringYesShort description of how duplicates were found.

Example request.

{"review_id": "rev-9f3c2a1b", "duplicates_removed": 87, "method": "Zotero duplicate merge, then manual title check"}

Example result.

{"ok": true, "duplicates_removed": 87, "records_identified": 412, "records_after_dedup": 325, "method": "Zotero duplicate merge, then manual title check"}

reviewer_record

Record reviewer type ('human', 'model', or 'unknown') and model identity.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
reviewerstringYesReviewer name (1 to 40 chars, stored lowercase). Cannot be primary.
reviewer_typestringYeshuman, model, or unknown.
model_idstringNoModel identifier (max 200 chars). Allowed only when reviewer_type is model.
run_refstringNoOptional run or configuration reference (max 200 chars).

Rules. Blinding and reviewer types are by convention, with an audit trail, not a guarantee. One agent can call tools under another reviewer's name, and two runs of the same model are not independent reviewers. Reviewer type is self-declared; no output may call a review verified or independent because of it. Reviewer primary is reserved for consensus decisions and cannot be given a type. Does not verify caller identity or authenticate models.

Example request.

{"review_id": "rev-9f3c2a1b", "reviewer": "screener_a", "reviewer_type": "model", "model_id": "example-model-1"}

Example result.

{"ok": true, "name": "screener_a", "reviewer": "screener_a", "reviewer_type": "model", "model_id": "example-model-1", "run_ref": null, "updated_at": "2026-10-30T08:23:23+00:00", "warnings": []}

screening_stage_set

Configure a screening stage mode ('blind' or 'unblinded') and its expected reviewers.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
stagestringYestitle_abstract or full_text.
modestringYesblind or unblinded.
reviewersarrayYesExpected reviewer names (for blind, at least 2 distinct reviewers, none primary).

Rules. Blinding is by convention, with an audit trail, not a guarantee. At an open blind stage, peer decisions and agreement are hidden until closed with screening_stage_close. Changing a closed blind stage back to blind fails, and so does making a stage blind after decisions are recorded at it. Does not enforce physical isolation.

Example request.

{"review_id": "rev-9f3c2a1b", "stage": "title_abstract", "mode": "blind", "reviewers": ["screener_a", "screener_b"]}

Example result.

{"ok": true, "stage": "title_abstract", "mode": "blind", "reviewers": ["screener_a", "screener_b"], "closed_at": null, "updated_at": "2026-10-30T08:23:23+00:00"}

screening_stage_close

Close an open blind screening stage and unblind peer decisions and agreement.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
stagestringYesStage to close: title_abstract or full_text.

Rules. Requires at least one paper with decisions by expected reviewers, and every expected reviewer must have recorded a decision for every paper any expected reviewer recorded at this stage. Fails and lists missing pairs if incomplete. On success, consensus decisions may be recorded under primary. Does not resolve disagreements or verify consensus.

Example request.

{"review_id": "rev-9f3c2a1b", "stage": "title_abstract"}

Example result.

{"ok": true, "stage": "title_abstract", "closed_at": "2026-10-30T08:23:25+00:00", "papers_count": 3, "decisions_count": 6, "reviewer_counts": {"screener_a": 3, "screener_b": 3}}

screening_record

Records one screening decision for one reviewer at one stage. Recording the same paper, stage and reviewer again updates the decision.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
paper_refstringYesDOI, pmid:<digits> or title:<title>|<year>.
stagestringYestitle_abstract or full_text.
decisionstringYesinclude or exclude; at full text also not_retrieved.
reasonstringFor excludeMaximum 300 characters.
reviewerstringNo1 to 40 characters, stored lower-case. Default primary.
titlestringNoOptional paper title for display.

Warnings. A full-text decision without a title/abstract include is flagged, and so is a title/abstract exclusion of a paper that already has a full-text decision.

Example request.

{"review_id": "rev-9f3c2a1b", "paper_ref": "10.1000/example.2021", "stage": "title_abstract", "decision": "include", "reviewer": "primary", "title": "Teleradiology turnaround in rural hospitals"}

Example result.

{"ok": true, "updated": false, "paper_ref": "10.1000/example.2021", "stage": "title_abstract", "reviewer": "primary", "decision": "include", "stage_counts": {"include": 48, "exclude": 277, "not_retrieved": 0}, "warnings": []}

screening_record_many

Records up to 500 screening decisions in one all-or-nothing call. An invalid item or a repeated paper, stage and reviewer returns an error with the item index, and nothing is written.

ArgumentTypeRequiredNotes
review_idstringYesExisting review id.
decisionsarray of objectsYesUp to 500 items with the same fields as screening_record.

Limits. Repeated (paper_ref, stage, reviewer) triples are rejected instead of silently overwriting. Use screening_record to update one decision.

Example request.

Limits and validation rules

Paper identity

Every paper_ref is stored in a canonical form. Accepted inputs are a DOI (lower-cased, with any doi: or doi.org prefix removed), pmid:<digits>, or title:<normalised title>|<year or nd>. Title matching folds accents and removes punctuation while keeping letters of every script. Anything else is refused. Use the same form for a paper in every tool, or later tools will treat it as a different paper.

How quote checks work

Quote matching ignores case, whitespace, curly quotes, dash variants, zero-width characters, line-break hyphenation and hyphens inside words. It needs at least 12 normalised characters and matches on word boundaries for scripts written with spaces.

An ellipsis quote (a ... b or a [...] b) verifies only when every part is found in order and the parts are at most 1,500 characters apart. In an evidence row, every number entered must also be written in the quote; missing numbers are reported in numbers_not_in_quote.

A failed check is stored and reported. It is never silently accepted, and it is never described as verified.

Data handling and privacy

Local storage

State lives in SQLite files under CITEPROOF_MCP_HOME, which defaults to ~/.citeproof-mcp. Each review is <home>/reviews/<review_id>.db. The server opens one file per review, applies its schema on first open, and uses WAL plus a 30 second busy timeout. Concurrent calls wait rather than fail as locked.

Source text is never stored in full. The server stores its length and SHA-256, plus observations and hash changes. Exports are returned as text; nothing is written outside the home folder. Removing or moving the folder moves the review data with it.

Network calls

The only network calls are DOI checks in verify_dois, to api.crossref.org and doi.org. Hosts are fixed, redirects are not followed, the timeout is 15 seconds, and a value that is not DOI-shaped is never sent. No review data is uploaded. Metrics, accounts and telemetry are not part of the server.

What stays on your machine

Review files, screening decisions, extracted evidence, claims, risk-of-bias records and source-text hashes stay in the local SQLite database. CiteProof does not receive them. The client can read tool results and may send them to its own model provider under that provider's terms; that is outside the MCP server's control.

Handling ok:false

Every handled failure looks like this:

{"ok": false, "error": "stage must be one of: title_abstract, full_text; got 'full_pdf'"}

Read error and change the argument. Common cases:

  • Invalid paper reference. Use a DOI, pmid:<digits> or title:<title>|<year>. Do not switch forms for the same paper.
  • Missing required field. An exclusion needs a reason; a supported or partial claim needs a quote and source text; an overall risk-of-bias judgement needs a rationale.
  • Wrong JSON type. The MCP SDK rejects the argument before the tool runs. That is a transport-level tool error, not an ok:false result.
  • Busy database. Retry the call. The failed attempt saved nothing.
  • Internal error. The message names the tool and exception type, with no stack trace or file path. Check the arguments, retry once, then report the tool name and a redacted request.

Read-only calls are safe to repeat. Do not blindly retry a write after an error that may have partially applied; read review_status first.

Without network access to install uv, the launcher falls back to a Python 3.12 that already has mcp, pydantic and httpx, or to the interpreter in CITEPROOF_MCP_PYTHON.
A DOI returns unverifiedThe registry was unreachable, so there is no verdict. It is not “not found”. Retry when the network is available.
Deduplication will not recordThe call did not cover every exported record. records_checked must equal the total hits recorded by prisma_record_search, or record the whole count with prisma_record_dedup.
An export is empty or cut shortCheck review_status for missing records and truncated in the export result. truncated is true when there are more than 5,000 screening decisions or claims. Each reviewer pair's agreement section lists at most 50 disagreements, and truncated does not report that cut. disagreement_count always holds the true number; call screening_agreement for the full list.
